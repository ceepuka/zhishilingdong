# 工作流管理配置

> 本配置文件是 workflow-manager Skill 在本项目的执行规范，必须被遵循。
> 基本模板即新项目初始化标准；本项目为已有项目，按现有文档结构对齐填充。

## 任务类型

### 单任务类型
| 类型 | 模式 | 场景 |
|------|------|------|
| 需求分析 | 完整流程（5步） | 分析目标、梳理需求、确定约束 |
| 设计任务 | 完整流程（5步） | 架构设计、功能设计、技术选型 |
| 开发任务 | 完整流程（5步） | 写代码、改文件、执行命令 |
| 测试任务 | 完整流程（5步） | 编写测试、执行测试、修复缺陷 |
| 文档维护 | 完整流程（5步） | 创建文档、更新文档、整理文档 |
| Bug修复 | 完整流程（5步） | 定位问题、修复代码、验证修复 |
| 重构优化 | 完整流程（5步） | 代码重构、性能优化、结构改进 |
| 发布任务 | 完整流程（5步） | 版本发布、变更日志、上线部署 |
| 查询任务 | 轻量模式（仅记录） | 解释代码、搜索内容、技术咨询 |
| 简单问答 | 不触发 | 简短回答、确认信息 |

### 多任务类型组合
| 用户意图示例 | 识别的任务类型组合 | 执行模式 |
|-------------|------------------|---------|
| 开发新功能 | 需求分析 + 设计任务 + 开发任务 + 测试任务 | 完整流程 |
| 修复Bug并验证 | Bug修复 + 测试任务 | 完整流程 |
| 重构并更新文档 | 重构优化 + 文档维护 | 完整流程 |
| 发布新版本 | 发布任务 + 文档维护 | 完整流程 |
| 分析需求并设计方案 | 需求分析 + 设计任务 | 完整流程 |

**组合规则**：
- 一个任务可能同时涉及多个类型
- 执行模式取组合中最高优先级的类型
- 日志需记录所有涉及的任务类型

## 执行步骤

### 第0步：读取核心文档
按任务类型读取相关文档（如存在）。**多任务类型组合时合并读取所有相关文档**。

**基础文档**（所有任务都读取）：
- `convention.md` — 文档约定与查阅优先级
- `lessons/` — 错误教训

> **注**：本项目未启用 `config.md`（见 [project-document-manager.md](project-document-manager.md) 文档清单），技术栈配置改由 `design.md` 第8节"技术栈"承载。

**按任务类型追加读取**：

| 任务类型 | 追加读取文档 |
|---------|-------------|
| 需求分析 | goal.md, prd.md |
| 设计任务 | design.md, refactor-history-module.md（如涉及历史模块） |
| 开发任务 | todo.md, design.md |
| 测试任务 | （手动测试，无 test-plan.md/test-results.md） |
| 文档维护 | docs/ 下的目标文档 |
| Bug修复 | issues.md |
| 重构优化 | design.md, refactor-history-module.md |
| 发布任务 | versions.md, history.md |
| 查询任务 | 按需读取相关文档 |

**多任务类型组合示例**：
| 用户意图 | 读取文档清单 |
|---------|-------------|
| 开发新功能（需求分析+设计+开发+测试） | convention.md, lessons/, goal.md, prd.md, design.md, todo.md |
| 修复Bug并验证（Bug修复+测试） | convention.md, lessons/, issues.md |
| 重构并更新文档（重构+文档维护） | convention.md, lessons/, design.md, refactor-history-module.md, docs/ 下的目标文档 |
| 发布新版本（发布+文档维护） | convention.md, lessons/, versions.md, history.md, docs/ 下的目标文档 |
| 分析需求并设计方案（需求分析+设计） | convention.md, lessons/, goal.md, prd.md, design.md |

### 第1步：理解需求
结合项目文档理解用户需求，不明确则引导澄清。**优先读取 [convention.md](convention.md) 确认查阅优先级**。

### 第2步：确认需求（可选）
根据任务类型判断是否需要确认：

**可跳过确认的任务类型**（脑力任务，难以量化判断）：
- 需求分析、设计任务、测试任务、文档维护、重构优化、发布任务

**按条件判断的任务类型**（操作任务，可量化判断）：
- 开发任务：满足全部条件可跳过（仅修改单个文件、≤20行、无删除、不修改接口）
- Bug修复：满足全部条件可跳过（同上）

**必须确认的情况**（参照旧 workflow.md 继承）：
- 需求模糊或多义
- 多种技术方案可选
- 重大架构变更
- 涉及删除文件
- 影响用户体验的改动
- 外部文件处理（用户偏好：必须先问用户具体要求）

### 第3步：执行任务
按确认的需求执行，失败则回滚并记录错误原因。

**执行规范**：
- 每次修改前先 `Read` 文件获取最新内容
- 使用 `Edit` 进行精确修改（避免 `Write` 覆盖整个文件，除非整篇重写）
- 修改后立即记录到 worklog.md
- 复杂任务使用 TodoWrite 创建任务列表（3步以上必须）

### 第4步：记录日志
写入 [worklog.md](worklog.md)，按下方日志格式记录。

### 第5步：汇总反馈
向用户汇总：执行了什么、改了什么文件、同步了什么文档。

## 回滚机制

执行失败时：
1. 检查已产生的文件变更
2. 如有部分变更，尝试回滚到执行前状态
3. 在 worklog.md 中记录回滚操作

## Git集成

- 是否启用自动提交：**否**（用户手动提交）
- 代码变更提交规则：用户主动要求时才提交
- 文档变更提交规则：同上
- 提交信息格式：遵循仓库现有风格
- 分支策略：在主分支开发

## 日志格式

### 完整流程任务
```markdown
## YYYY-MM-DD（任务简短主题）

- **任务类型**：{单类型 / 多类型组合，如：需求分析+设计+开发}
- {时间} 理解需求：{摘要}
- {时间} 确认需求：{结果}
- {时间} 执行任务：{内容} → {状态}
- {时间} 记录日志：完成
- {时间} 汇总反馈：{反馈内容}
```

### 轻量模式任务（查询）
```markdown
## YYYY-MM-DD

- {时间} 查询：{问题} → {要点}
```

## 协同规则

任务产生文件变更时：
1. 提示用户可触发文档同步（project-document-manager Skill）
2. 涉及代码变更时，运行 `npm run build` 验证（参照旧 workflow.md 验证规范）
3. 涉及 PRD 变更时，按 [convention.md](convention.md) 3.1 PRD 更新规则同步 goal.md / todo.md / history.md
4. 在 worklog.md 中记录所有涉及的文件变更

## 项目特定规范

1. **PRD 是需求唯一真实来源**：所有功能需求以 [prd.md](prd.md) 为准
2. **代码实现 > 所有文档**：文档与代码冲突时以代码为准，并触发文档同步修正
3. **外部文件处理**：不确定用途的外部文件必须先问用户具体要求再行动
4. **死代码处理**：开发期被替代/无引用的代码直接删除（不备份、不留兼容层），删除后同步更新文档。例：`src/modules/visual/` 已于 2026-09-04 删除
5. **知识图谱 vs 知识目录**：实际实现的是 div 层级"知识目录"，非 SVG 知识图谱
6. **6 种知识卡片**：组件已存在但未接入主流程，标记为"未完成/待优化设计"
7. **AI 密钥**：通过 UI 配置（LocalStorage），不使用环境变量硬编码
8. **构建验证**：每次代码修改后必须运行 `npm run build`
