# 逻辑错误

## viewingQuery标识一致性原则：历史记录匹配必须使用原始输入
- 时间：2026-07-12
- 场景：文档生成模块"浏览中"状态不显示 - AI修改标题导致匹配失败
- 错误：viewingQuery 使用 result.title（AI可能修改用户输入的标题），而历史记录的 item.query 是用户原始输入的topic，两者不一致导致"浏览中"标记不显示
- 原因：AI生成内容时可能修改、润色用户输入的标题，result.title ≠ 原始query，但历史记录的标识是原始query，匹配依赖 === 精确比较
- 正确：任何需要与历史记录/收藏等外部数据匹配的场景，都要使用**稳定不变的原始标识**（用户输入的query/topic），不能使用可能被修改的派生值（如AI生成的title）。各模块统一使用 currentTopic/currentQuery 等状态变量跟踪原始输入。
- 标签：历史记录, 浏览中, 标识一致性, viewingQuery, 状态匹配, AI生成

## AI生成内容需要专用渲染器，不能用纯文本标签
- 时间：2026-07-12
- 场景：文档生成模块结果显示 - AI生成的Markdown内容用pre标签只能显示纯文本
- 错误：使用 `<pre>` 标签显示AI生成的文档内容，导致标题、列表、代码块等Markdown格式无法渲染，只能显示纯文本
- 原因：AI生成的内容通常是结构化格式（如Markdown），包含丰富的格式信息，纯文本标签无法解析这些格式
- 正确：根据AI返回的内容格式选择对应的渲染器。Markdown内容使用 react-markdown + remark-gfm 渲染，HTML内容使用 dangerouslySetInnerHTML，纯文本才使用 pre 标签。内容格式应作为数据契约的一部分明确。
- 标签：Markdown, AI生成, 渲染, react-markdown, 富文本, 内容格式

## 模式隔离原则：不同模式的状态必须完全独立
- 时间：2026-07-11
- 场景：搜索/问答模式串扰 - 两个模式共享状态导致数据混乱
- 错误：搜索模式和问答模式的状态管理有交叉，切换模式时状态没有完全隔离，导致一个模式的内容影响另一个模式
- 原因：多个模式共用部分状态变量，切换模式时只改了UI但底层数据没有完全隔离
- 正确：不同模式（搜索/问答、查词/翻译）的状态必须**完全独立**，各自管理自己的数据。切换模式时使用 React key 强制组件重挂载，或使用完全独立的状态变量。历史记录也按类型分开存储和展示。
- 标签：模式隔离, 状态管理, 串扰, 多模式, 搜索, 问答

## 树状布局子树范围计算：用topOffset/bottomOffset替代单纯subtreeH
- 时间：2026-07-11
- 场景：思维导图布局算法重构 - 叶子节点描述外置导致垂直对齐偏差
- 错误：仅用subtreeH表示子树总高度，假设节点中心 = 子树中心，但叶子节点带描述时节点在子树顶部而非中心，导致父节点与子树垂直错位
- 原因：子树高度是"总高度"，但节点在子树中的相对位置不固定（可能在顶部、中心或底部），仅靠subtreeH无法还原节点的精确位置
- 正确：使用 `topOffset`（节点中心到子树顶部的距离）和 `bottomOffset`（节点中心到子树底部的距离）两个值替代单纯 `subtreeH`。测量阶段计算每个节点的topOffset/bottomOffset，布局阶段用 `child.topOffset` 定位子节点中心，确保精确对齐。
- 标签：布局算法, 树状结构, 递归, 子树测量, 对齐, 思维导图

## 跨组件共享状态 Hook 的正确模式
- 时间：2026-07-07
- 场景：收藏功能重构 - WordResult/SentenceResult/DocResult 各自直接操作 localStorage
- 错误：各组件各自读写 localStorage 并手动 dispatch 自定义事件通知其他组件，代码重复且容易出现同步延迟
- 原因：`useState` 创建的是组件级独立状态，不同组件调用同一 hook 获得的是各自独立的 state 副本
- 正确：使用 `useSyncExternalStore` + 模块级变量 + listeners Set 模式。所有 `useXxx()` 调用共享同一份模块级数据，`addFavorite`/`removeFavorite` 直接修改模块级变量 + notify 所有 listeners，`useSyncExternalStore(subscribe, getSnapshot)` 确保所有组件即时同步。参考代码：`src/hooks/useFavorites.ts`
- 标签：useSyncExternalStore, 共享状态, hook, 模块级变量, 收藏, localStorage

## 消息数组多余反转导致导出顺序错误
- 时间：2026-07-05
- 场景：知识搜索模块 - 对话复制/导出功能（QASection）
- 错误：`formatQAText` 函数中对消息数组使用了 `.reverse()`，导致导出的 Q&A 文本顺序反转（最新在前）
- 原因：消息存储时使用 `[...prev, newMsg]` 追加，天然就是旧→新顺序；渲染时直接 `.map()` 也是旧→新从上到下。format 函数不应再反转，否则与渲染顺序不一致
- 正确：消息存储（append）、渲染（直接 map）、格式化（直接 map）三者保持一致的顺序，不需要任何 `.reverse()`
- 标签：消息顺序, reverse, chat, 数组, 导出

## 流式增量解析：字段"完成"判定必须覆盖所有值类型
- 时间：2026-09-11
- 场景：搜索模块流式渲染 - 步骤指示从第二个字段起一直卡在"正在生成知识导图"，总述也延迟显示
- 错误：`StreamingJSONParser.scan()` 只在**字符串/字面量**型值收尾时登记 `completedKeys`；值为**数组/对象**的顶层字段（`mindMap`/`concepts`/`knowledgeContext`/`examQuestions`/`interestingFacts`）收尾发生在子帧弹栈之后，父帧拿不到"值已结束"信号，导致中间态 `completedKeys` 整类缺失。下游 `deriveStep()` 取"第一个未完成字段"，于是永远返回 `mindMap`
- 原因：JSON 值的收尾方式因类型而异 —— 字符串/字面量在**所属帧内**收尾，容器在**自己的子帧**收尾；只处理其中一种就会漏掉整类字段。且最终态回退到 `Object.keys(data)`，把"中间态字段清单缺失"完全掩盖，所以只在流式过程中可见
- 正确：容器闭合弹栈后，若父帧正是根对象且 `pendingKey` 非空，立即登记该顶层字段完成。通用原则：**增量解析的契约必须在"未闭合"状态下断言** —— 最终态往往有兜底逻辑，只有中间态测试才能暴露这类缺陷；另外，mock 数据源若手工构造增量（而非走真实解析器），该 bug 永远不会在 mock 下复现
- 标签：流式, StreamingJSONParser, completedKeys, 增量解析, 中间态, 步骤指示, 思维导图, 测试盲区

## 带"自愈"承诺的熔断/缓存必须保证自愈入口可达
- 时间：2026-09-11
- 场景：流式能力黑名单（`baseAIProvider.ts` 的 `streamUnsupported`）导致某型号一次流式失败后，整个会话内容不再逐段生长、而是憋很久整段一次性出现（"分析早就有历史记录了，summary 却迟迟不显示"）
- 错误：黑名单用 `Set` 实现"一次失败永久记入"，之后 `prepareRequest` 永远算得 `wantStream = false`，`callModelStream` 直接走非流式分支。但代码注释承诺"流式成功即 `markStreamSupported` 移出（自愈）"—— 该路径要求后续请求真的发出 `stream:true`，而永久禁用后**永远不会再发流式请求**，于是自愈逻辑成为**永远走不到的死代码**。黑名单实际退化为"整个会话关掉该型号流式"。
- 原因：把语义上的"冷却（临时降级 + 到期重试）"实现成了"永久禁用"，两者在无测试时几乎无法区分；且故障表现（不再流式）与实现（降级为非流式）距离很远，排查成本极高。进程内缓存、刷新即恢复，进一步掩盖问题。
- 正确：熔断类缓存用 **`Map<key, failedAt>` + 冷却期（`STREAM_RETRY_COOLDOWN_MS`）** 实现：无记录放行；冷却期内临时降级；**冷却期结束自动重试**（自愈入口可达）；成功即删除。同时遵循两条配套原则：① **运行时降级必须可观测** —— 凡行为随进程内状态变化的分支都留 `console.warn`，静默降级等于把 bug 藏起来；② **记账条件收敛到"证据"层** —— 只有协议层明确失败（响应非 SSE 增量 / SSE 解析失败 / 传输层失败）才记黑名单，"收到思维链但正文未到"证明服务端在流式，不算失败。降级策略必须有契约测试，用可注入的 `now` 钉死冷却边界。
- 标签：熔断, 自愈, 流式黑名单, streamUnsupported, 冷却期, 降级, 可观测, baseAIProvider, 契约测试

## AI 内容渲染入口必须统一 + 防御性回退
- 时间：2026-09-11
- 场景：用户实测发现关键要点列表里 `$\vec{F}$` 原样露出、试题题干里 `\triangle ABC` / `\sqrt{13}` 原样露出；"公式报红"反复出现（同一类问题在多个字段重复发生）
- 错误：① `LatexText` 只接入 11 个文本字段，遗漏 `keyPoints` / `pitfalls` / `learningPath` / `confusables` / `mindMap` 节点标题·描述 / `interestingFacts.title` / 标签 chip —— 同一组件"有的字段渲染、有的裸露"，是结构性漏洞；② `MATH_SPLIT` 只认 `$...$` / `\(...\)` 围符，模型在试题里大量输出裸 LaTeX（无围符）走过渲染器也照样原样露出
- 原因：① **零散接入是漏洞温床** —— 同一类数据要么全部走同一个渲染器，要么全部别用；约定"AI 应当写 `$...$`"是软约定，渲染层必须有硬兜底；② **只认显式围符是被模型风格牵着走** —— 显式约定不灵时（模型不听话）没有兜底手段
- 正确：① **统一入口**：所有 AI 文本字段都过同一个渲染器，零遗漏用测试钉死（`searchResultsLatex.test.tsx`）；② **防御性识别**：`splitBareLatex` 只认强信号（反斜杠命令 `\\[a-zA-Z]{2,}` + 带花括号上下标 `[\^_]\s*\{`），**必须 KaTeX 解析成功才渲染**（既挡 `snake_case` 误识别，也挡 `C:\Users` 这类伪命中），失败一律原样输出绝不吞内容 —— 最坏情况是回到原文，不出错位；③ **prompt 源头加固**：在系统提示词里**置顶**"凡数学符号一律 `$...$$` 包裹"+ 正反例（`$\triangle ABC$` vs `\triangle ABC`），让模型源头干净、渲染层兜底
- 标签：渲染入口, 统一处理, LatexText, 裸 LaTeX, 防御性渲染, KaTeX, splitBareLatex, prompt 兜底

## "吞错器"会让下游错误处理变成死代码
- 时间：2026-09-12
- 场景：搜索页卡在「模型正在思考…已等待 511 秒」；为超时补的状态机识别分支实测不生效
- 错误：`withFallback` 包装层把**任何异常**都 catch 成 fallback 空结构体 + `success:true`。于是 `callModelStream` 抛出的 `StreamTimeoutError` 在中间就被吞掉，状态机里针对它的识别分支**永远走不到**（死代码），用户只看到笼统"生成失败"
- 原因：兜底层与错误处理层职责重叠 —— 一个"什么都兜底"的包装器会静默改变所有下游的前提假设；且症状（笼统失败）与原因（链路超时）距离极远，排查成本高
- 正确：兜底层必须**区分错误语义** —— "业务错误"可兜底（返回 fallback），"链路/传输错误"（`StreamTimeoutError`/`StreamProtocolError`）应**透传**为 `success:false + code`，由上层决定提示与重试。凡"包一层 catch 全部兜底"的写法，先问一句：下游还需不需要知道真实失败原因？
- 标签：错误处理, withFallback, 吞错, 死代码, 链路错误, 透传, 兜底, 超时

## 同一语义不要有两套实现：续写判定必须与解析层同源
- 时间：2026-09-12
- 场景：超限续写判定"JSON 是否写完"漏判数组未闭合，内容半截收尾
- 错误：`hasCompleteJSONObject` 自己写了一套括号配对，只跟踪 `{}` 不跟踪 `[]` —— `{"a":[1,2}` 数组未闭合，却因 `}` 让花括号深度归零被误判"完整"，从而跳过续写。而解析层 `StreamingJSONParser.scan()` 早已正确处理 `{}`/`[]` + 字符串转义 + markdown 围栏，两套实现必然漂移
- 原因：同一语义（"JSON 是否完整闭合"）被重复实现，一处修复不会同步到另一处；手工实现的边界覆盖远不如久经测试的解析器
- 正确：导出解析层权威判定（`isCompleteJSON` / `analyzeJSON`），业务层直接复用，消除重复实现；并在"括号闭合"之上补足**语义判据**（`buildGenerateCompleteChecker` 要求核心字段齐全），因为"括号闭合 ≠ 内容完整"。凡"完整性 / 有效性判定"都应指向同一权威实现
- 标签：同源, 单一实现, hasCompleteJSONObject, isCompleteJSON, 续写, 完整性判定, 边界, 解析

## 思考型模型的默认思考必须显式关闭，且参数逐厂商核对
- 时间：2026-09-12
- 场景：用户反馈"智谱模型很多时候没有内容渲染、总是生成失败；千问正常"
- 错误：智谱 GLM-5.2 默认开启深度思考，先输出大段 `reasoning_content`；且智谱 `max_tokens` 是**思维链 + 正文总预算**，思维链吃满后正文 JSON 被 `finish_reason=length` 截断 → 续写也失败。千问正常仅因它被显式关闭了思考。更隐蔽的是：关闭思考的**字段名逐厂商不同**（千问 `enable_thinking` / 智谱 `thinking:{type:'disabled'}` / DeepSeek `reasoning_effort`），智谱传 `thinking:false` 会直接 400

- 标签：思考模式, reasoning, max_tokens, 智谱, zhipu, enable_thinking, DISABLE_THINKING_PARAMS, 厂商差异, 生成失败

## 约束 LLM：负面限制不如正向可执行教学
- 时间：2026-09-12
- 场景：模型编造答案（电路题答案写"最大功率 9W"、解析却算出"8W"）、解析里自我怀疑瞎猜（"改原题更可能问的是另一角"）；AI 画图不符合学科惯例
- 错误：prompt 里全是"要准确""别画错""画不准就空字符串"这类**负面限制** —— 模型不知道"怎么做才对"，只知道"不许做什么"，无从执行
- 原因：LLM 需要的是**可执行的步骤**与**可判定的准则**，而不是形容词式约束；负面限制无法告诉模型"正确长什么样"
- 正确：① 把"限制"翻译成**正向步骤**（画几何图：先定三顶点坐标 → 按对边命名 a=BC → 补直角符号 / 等长标记 / 角弧）；② 把"要准确"翻译成**反例句 + 判定准则**（"答案与解析不一致""不准出现'改原题'类措辞""不确定就 `examQuestions: []`"）；③ 纯文本模型做不到的事（输出原图 base64）要**显式禁止**并给替代路径（可信直链 / 手绘 SVG / 干脆不出这道题）
- 标签：prompt, 负面约束, 正向教学, 编造, 幻觉, SVG, 配图, 严谨性铁律

## 提示词句式：句式改写只适用于"条件/禁止描述复杂"的句子
- 时间：2026-09-12
- 场景：`buildGeneratePrompt` 里散布"不要画成弧""不要实心点""禁止 <script>""不要任何前后解释""不要省略字段"等否定式约束；第一轮我曾**机械地把每一条都改写成"必须……否则……"**（如"禁止 <script>"→"必须不使用 <script>…；否则图形会被渲染器拦截而完全不显示"），被用户指出是**过度改写、生搬硬套句式**
- 错误：把一个句式当成万能模板，**不看句子本身是否复杂**就统一套用；对本来就短小明确的硬性规则（安全限制、格式约束）额外补"否则……"解释，反而增加噪声、稀释重点
- 原因：句式改写的价值在于**消歧**，只有当原句确实难读时才成立 —— 即用户说的"**'在什么……的条件下'或'……不要做……'太复杂的描述**"。原句已经清晰时，改写只是换皮，附带的长解释还会让模型注意力分散
- 正确：**按原句复杂度分档处理**
  - **保留原样**（短小、明确、无歧义，尤其是安全/格式硬性规则）：`禁止 <script>、事件属性、外部图片引用、<use>、url(http...)。` / `只返回 JSON 本身，不要任何前后解释、不要 markdown 代码块` / `直角……不要画成弧` —— 越短越有效，**加解释是减分**
  - **改写为"必须 X，不得 Y，否则 Z"**（条件句 / 多重禁止 / 需要消歧的复杂描述）：如"交叉处若非连接点不要画实心点"→"**必须**用横平竖直的折线连接各元件；交叉处若非连接点，**不得**画实心点，**否则**会被误判为连通节点"；"如果前面是 JSON，就继续合法的 JSON 文本（……），不要重新开始一个新的 JSON"→"**必须**严格延续原有格式：前面是 JSON 就继续合法的 JSON 文本（……）；**不得**重新开始一个新的 JSON"
  - 反例措辞要"通常化"："答案与解析自相矛盾"写成像"答案是 1、解析却是 2"这种跨题型都成立的例子，比"9W/8W"这类具体数值更具迁移性
- 标签：prompt, 句式, 必须否则, 否定约束, 正向指令, 提示词治理, 过度改写, 复杂度分档

## 约束补全：限制处要补"应该怎么做"，并显式要求 AI 自检
- 时间：2026-09-13
- 场景：`buildGeneratePrompt` 里不少限制句**只写了禁令、没写正向替代**（如"不要编造 URL""不编造""不得硬填一个无关的图"）；且 AI 画完 SVG 后**不主动核对**，常输出"顶点没闭合、标记标错位、数值与题干不符"的错图
- 错误：① 只给"不许做什么"，模型不知道"该做什么"，遇到边界只能猜；② 默认 AI 会自己检查输出，但 LLM 生成即输出、**不会主动回溯核对**
- 原因：负面约束缺正向动作时，模型没有可执行路径；自检不是模型的默认行为，必须显式下达"输出前逐条核对"的指令
- 正确（三档语法 + 自检）：
  - **简单禁令保持原样**（`禁止 <script>`、`只返回 JSON 本身`、"直角不要画成弧"）—— 不补长解释
  - **复杂条件句**用"**必须 X，不得 Y，否则 Z**"（如导线交叉、续写延续格式）
  - **"限制处缺怎么做"补正向动作**：用"**应该 X，而不是 Y**"对照——"不要编造 URL"→"拿不准时应该留空字符串（交给检索兜底），而不是编造 URL"；"不编造"→"不确定处应该明确说明存疑，而不是编造"
  - **显式自检清单**：SVG 段末尾新增【画完自检】，要求"输出前必须逐条核对"——关键点闭合 / 标记对号 / 数值一致 / 符号规范 / 没有多余元素，并写"发现任何一处对不上，必须回到对应步骤重画，而不是带着错误输出"
  - **自检项本身也要带"怎么检查"**（2026-09-13 补充）：自检清单不能只写"检查什么"（如"点是否画对""元件是否连上"），**每条必须写清"检查的方法"**——"点是否画在线上 → 把点坐标代入它应在的线/圆方程看是否成立"；"函数图象是否过对点、是否在对象限 → 把题干坐标代入函数式验证 + 对照斜率/二次项符号"；"元件是否连进电路 → 沿电流路径从正极走一遍回路，看能否流经每个元件再回负极"。只给"检查什么"不给"怎么检查"，AI 仍只会凭印象扫一眼、继续漏错
  - **字母代号的位置也要检查**（2026-09-13 补充）：角/边/顶点/物理量/元件的字母代号**必须各归其位**——角的字母写顶点旁（不能写边中间）、边的字母写边中点旁（不能写顶点）、力的符号标箭头旁、元件代号标元件旁、x/y/O 各归其位。这是高频错位点（"角的字母写在边中间"），要**单独成条**、并给出检查方法（逐个字母问"它代表哪个对象，是否紧邻该对象"）
  - **自检项要按学科/类型拆分，只让 AI 看高度相关的内容**（2026-09-13 用户明确要求）：当自检项覆盖多个不相干场景（几何/函数/电路/受力/光学五类图），**必须拆成「通用自检（必查）+ 分场景自检（只查当前那类）」**，并写"**只套用与当前图相关的条目，无关条目不要套用、不要去想**"。否则一长串混合清单会**让无关内容干扰 AI 对当前图的判断**——AI 注意力有限，看到的规则越多、越容易串味
- 标签：prompt, 正向动作, 应该而不是, 自检, 核对, 检查方法, 代号错位, 分学科拆分, 无关内容干扰, SVG, 画图检查, 提示词治理

## prompt 产出字段必须全链路闭环（否则静默空白）
- 时间：2026-09-13
- 场景：知识图谱"不显示任何内容"。`graphData` 字段在类型定义、状态机（`isSpecific=false` 时读 `analysisResult.graphData`）、UI 组件三层都备好了，唯独 `analyze` 的 prompt 从没要求模型产出 `graphData`，所以它永远 undefined
- 错误：字段在"消费端"（类型/状态机/UI）都接好了，但"生产端"（prompt）漏了让模型输出这个字段
- 原因：一个 AI 产出字段的完整链路是 **prompt（要求产出）→ 类型（定义）→ 清洗（sanitize）→ 状态机（传递）→ UI（渲染）**，缺任何一环都表现为"没数据/空白"，且因为不报错、极难定位
- 正确：
  - 新增一个"AI 产出的结构化字段"时，**逐环核对这五段**：prompt 是否明确要求产出并给了字段示例（含 JSON 示例）→ 类型是否有该字段 → 是否有 sanitize 兜底（AI 结构不可信）→ 状态机是否透传 → UI 是否消费
  - **prompt 的返回 JSON 示例要包含新字段**，否则模型不会主动产出
  - sanitize 要对"缺字段"给兜底（如 graphData 节点缺 category 从父继承、根节点缺 category 用 title），否则真实 AI 的脏数据会再次触发渲染异常
- 标签：全链路闭环, prompt 产出, graphData, 静默空白, sanitize, 字段缺失, 知识图谱

## "原样输出、绝不吞内容"要配视觉信号 + Prompt 防御要写"具体怎么错"
- 时间：2026-09-13
- 场景：对话里大量公式渲染失败，模型把 `\` 吞了（`\frac` → `rac`、`\triangle` → `riangle`、`\sqrt` → `sqrt`），整段公式露源码；`LatexText` KaTeX 失败时**原样裸输出**（"绝不吞内容"），用户看不到视觉信号
- 错误：① 渲染层只做"原样输出"兜底，没给视觉信号；② Prompt 只写"用 LaTeX"，没强调"反斜杠绝不能省"也没给反例
- 原因：①"原样输出"对屏幕阅读器/复制/测试是安全，但对用户的视觉体验是"页面 bug"——视觉信号不破坏 textContent，可以双得；② Prompt 防御要给"具体怎么错"的反例，模型才能识别"这是错的"的具体形态
- 正确：
  - **渲染层兜底 + 视觉信号双得**：`LatexText` KaTeX 失败时把那段包在 `<code class="latex-fallback">`（等宽字体 + 浅琥珀背景 + 左侧细色条 + `title="公式源码（未能渲染）"`），`textContent` 仍为原文（屏幕阅读器/复制/测试不受影响）
  - **Prompt 防御要写"具体怎么错"**：把"公式书写规则"升格为"最高优先级、逐字符保留"，给出 `'\frac' 不能写 'rac'`、`'\triangle' 不能写 'riangle'`、`'\sqrt' 不能写 'sqrt'` 的反例，以及"不得简写 `\frac{a}{b}` → `a/b`"的禁令
  - **对话气泡视觉密度需单独调**：消息气泡加 `leading-relaxed + break-words + whitespace-pre-wrap + py-2.5`，让密集公式呼吸
- 标签：原样输出, 视觉信号, latex-fallback, 反斜杠, Prompt 防御, 反例, 对话密度

## 模板字符串里写 LaTeX 反例要防"反斜杠被解析"
- 时间：2026-09-13
- 场景：在 `buildFollowupSystemPrompt` 里写 `'\frac' 不能写 'rac'` 这种 LaTeX 反例，写完发现契约测试不通过——运行时字符串里反斜杠消失了
- 错误：源里写 `'\frac'`，JS 把 `\f` 当成 form-feed（ASCII 12 控制字符）解析，运行时变成 `'<form-feed>rac'`，反斜杠消失
- 原因：JS 模板字符串里 `\<字符>` 是转义序列（`\n` 换行、`\t` 制表、`\f` 换页、`\\` 反斜杠等），源里必须写 `\\frac`（双反斜杠）才能得到运行时单反斜杠
- 正确：
  - 模板字符串里要写"运行时一个反斜杠"，源里必须写 `\\`（双反斜杠）
  - 写完用 `node -e` 或 grep 验证运行时字符串里**反斜杠真的存在**（不要看源，源有 `\\`，运行时才是 `\`）
  - 这是 MEMORY 里"prompt 改写绝不能引入反引号"的同类陷阱：**模板字符串里的转义字符会被吃**，必须用工具验证
- 标签：模板字符串, 反斜杠, form-feed, 转义, 运行时验证, 提示词治理

## 解析/开放文本字段要"总闸式"禁止离题，不能只靠"与答案一致"
- 时间：2026-09-13
- 场景：试题解析（`examQuestions[].explanation`）里出现"几道经典题""信雅达千字文""采用 2022 年全国乙卷真题"等离题乱编，还有多套解法交织、互相矛盾
- 错误：只约束了"解析必须与答案一致""解析给出确信推导"，**没写一条总闸式禁令**禁止解析里出现离题话术（自我标榜、罗列多题、引言点评、多套解法）
- 原因：模型对"开放文本字段"（explanation 这类自由书写）容易失控——它会把"写解析"扩展成"先铺垫背景、再点评题目、再给多种解法"，而这些都不在"与答案一致"能管住的范围内；"与答案一致"管的是**结论正确**，管不了**过程里夹带的废话**
- 正确：
  - 对开放文本字段，除了"结论正确"，还要加一条**总闸式禁令**：只许写"解这一道题"的分步推导，一步到底、一套解法；**严禁**出现具体离题话术（"这是真题/经典题/易错题""本题考的是……""下面讲几道题"等），并把它们作为反例列出
  - **字段级约束 + 严谨性铁律双写**：既在字段说明（第 6 点）写清 explanation 的写法，又在顶层的"严谨性铁律"补一条总闸，双重兜底
  - **续写提示词也要防"推翻前文"**：续写时明确"不得推翻/改写/重新解释前面已写结论，顺着往下接"，否则模型在续写轮会重述或改写前文，造成"多套解法交织"
- 标签：离题, 解析, explanation, 总闸, 自我标榜, 多套解法, 续写, 开放文本字段
